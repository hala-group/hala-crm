# Hala CRM decisions

## Legacy self-chat display names (2026-11-23)

- A read-only production check confirmed that the linked account's own JID/LID were correct, while a different contact still had the old generated display name `أنت (الرقم الحالي)`. The display helper rejected `أنت` and `أنت (رسائل شخصية)` as fallback names, but allowed this historical variant to appear as an ordinary contact name.
- Recognize these reserved self labels, including harmless whitespace/bidi variations, only as synthetic placeholders when choosing a fallback name. The self-chat designation still comes from the source account's verified identity. For other contacts, prefer their real sender name or phone. No production contact, identity, message or conversation rewrite is required.

## Grouped message push (2026-11-22)

- At the user's request, show one updated notification per tenant/account/recipient/conversation, including the stored unread count and latest message preview. Counts follow the existing shared conversation read state; they are not an independent per-device unread counter. The first notification respects OS defaults, while updates to a visible conversation notification are silent.
- Extend the existing Angular registration with `hala-sw.js`, importing the installed NGSW runtime in the same root scope. Do not add Firebase's competing worker or replace the existing Push subscription/VAPID pair. Register the narrowly marked message-push listener before importing NGSW so it can stop NGSW from also rendering that push; all other push and click events retain Angular handling. This ordering deliberately differs from Angular's generic import-first example to prevent duplicate display. Keep Angular's PUSH client broadcast contract for handled messages.
- Server payloads include scoped grouping metadata in both FCM data and web notification data, plus a stable tag and `renotify: false` as a fallback for clients awaiting the worker update. The worker serializes updates per tag, checks visible notifications, ignores stale revisions/duplicate message IDs, explicitly closes replaced notifications, and preserves newer preview content if events arrive out of order. Reading a chat locally closes its notification; logout/disable closes this recipient's visible message notifications. No message history is persisted in worker storage.
- Keep title/body/photo previews subject to the existing fresh CASL recipient checks. Browser and OS control final notification appearance and support. No new dependency or environment variable is needed. Implementation references: installed Angular 22.2.4 NGSW `handlePush`/`handleClick`, Angular custom worker documentation, and the Notifications API `getNotifications`, `tag`, `silent` and `renotify` contracts.
- Keep grouping metadata compact and bound preview/title sizes by UTF-8 bytes, including emoji, to leave room for signed sender photos within FCM's message size limit. The notification body is reused instead of copying message content into both metadata envelopes.

## Durable account cleanup (2026-11-22)

- Account deletion and clear/reimport now return HTTP 202 after queuing an authorized cleanup. Their progress is persisted on the account and exposed through the existing scoped account views; retrying a failed operation resumes remaining media records. Both connected and disconnected Baileys accounts can clear chats.
- Operational extension to the spec: the API runs a BullMQ cleanup consumer alongside its HTTP entrypoint, reusing its existing scoped repositories, audit and storage registry. WhatsApp sessions remain exclusively in the WhatsApp worker and are stopped through its existing command/lease boundary. No new service, package or environment variable is required. BullMQ 6.7.1 package types are the source for worker lifecycle and retry options.
- The account is locked against reconnect/history changes until cleanup finishes. Delete stored files with bounded concurrency and remove each media record only after all of its files were deleted; missing files are already idempotent in each storage adapter. Failed/pending assets are still cleaned because their status does not prove no remote file exists. Redis persists queued jobs across API restarts; completed jobs expire after one day. A failed account card offers explicit retry and retains the cleanup lock.
- Successful clear/reimport requests a new QR pairing only after cleanup and audit finish. Internal jobs execute the tenant and CASL scope accepted when the destructive action was authorized, with no user credentials in job data. Unexpected HTTP errors log a sanitized error name and stack locations, never exception messages or request payloads.

## Contact identity and sender names (2026-11-19)

- Message `pushName`, `senderPn` and `senderLid` identify the sender. On outgoing direct messages they must never rename or alias the recipient. Validate the same rule again in inbound persistence so queued older events cannot reintroduce the corruption.
- Self-chat presentation is account-specific. Compare the conversation contact's primary WhatsApp identity with the connected account's verified PN/LID identities; do not infer ownership from a saved name or a tenant-wide `isSelf` flag. Persist the account's own normalized identities from the active provider connection. Reserved legacy self labels on unrelated contacts fall back to a verified name or phone number.
- Correct only confirmed affected production contact fields, with scoped preconditions, an encrypted before-image and an audit entry. Do not merge/delete conversations or messages, guess missing names from message text, or rewrite other contacts merely because names coincide.
- Verification: lint, typecheck, the full test suite and builds pass. Regression coverage includes outgoing PN/LID sender metadata, old queued events, shared contacts viewed under different accounts, namespace collisions and removal of a previous account owner's identity on relink. A production dry run confirms three affected contacts; one retains another available name and two fall back to their phone numbers. Eight available cached history batches contained no further verified names for these targets.

## Compact mobile inbox (2026-11-19)

- At the user's request, move the mobile navigation into a modal side drawer, keep search and an icon-only new-conversation action on one row, and put a compact account-color selector beside the inbox title. The selector retains account labels, phone numbers and the selected state in its popup; color never becomes the only accessible identifier. Desktop navigation remains inline.
- Use the browser's native modal dialog for focus containment, Escape dismissal and focus restoration. Keep one permission-filtered navigation template for desktop and drawer. Reuse the existing account filter and send permissions; no new API or dependency is needed. Size the mobile inbox from the single-row app header so the conversation list uses the remaining viewport height.
- Verification: `pnpm lint && pnpm typecheck && pnpm test && pnpm build` passes (182 tests, two existing optional tests skipped). Six Playwright checks against the production build pass at 320/390/720px plus desktop: no page overflow, search/new-chat alignment, modal dismissal and focus behavior, account selection/filter requests, selected colors, permissions and desktop navigation. Local browser QA used the installed Edge with isolated API fixtures; no customer data or real messages were used.

## WhatsApp history import (2026-11-07)

- **Fresh pairing history sync (2026-11-07):** On a new Baileys QR pairing, request automatic full history with the macOS desktop browser preset and `syncFullHistory: true`, and keep that mode through the QR handshake restart. An already registered session retains the Ubuntu preset; switching its browser profile during a live import caused repeated `Connection Terminated` errors. This extends the Phase 3 inbound pipeline without adding a file export workflow. Baileys receives only the history WhatsApp offers and can decrypt; connecting successfully is not proof that old messages arrived.

- **Fresh session detection (2026-11-08):** Treat an auth state as a new QR pairing only when it has no saved WhatsApp identity (`creds.me` or `creds.account`). Live credentials contained both identity fields but `registered: false`; using `registered` alone incorrectly switched that existing session to the macOS browser and caused repeated `Connection Terminated` errors. The in-memory pending flag still carries full-history mode through the immediate QR restart after a genuinely fresh pairing.

- **Fresh pairing browser fallback (2026-11-08):** Live verification of a genuinely fresh QR pairing showed that WhatsApp closed the macOS desktop Baileys socket with `Connection Terminated` before it could show a QR code. The worker therefore uses its proven Ubuntu browser preset for both new and existing sessions while requesting `syncFullHistory: true` on fresh pairing. This differs from the Baileys history-sync guide's macOS recommendation; the resulting history amount must be measured after QR pairing and may be incomplete.

- **History placeholder filtering (2026-11-08):** Baileys history can contain `E2E_ENCRYPTED`, `E2E_ENCRYPTED_NOW`, and `CIPHERTEXT` stub records with no user message body. These transport notices are ignored by the inbound normalizer so they do not create false inbox conversations. Historical rows already stored from these notices require separate targeted cleanup; actual user message rows are retained.

- **History import behavior (2026-11-07):** The first implementation restarted the owned Baileys session with `syncFullHistory`; live verification showed repeated `Connection Terminated` failures. History import now uses Baileys `fetchMessageHistory` against the existing live session and the oldest stored message for each known conversation (up to 100 older messages per conversation per request), using the original WhatsApp JID where available for LID chats. `messaging-history.set` messages go through the idempotent inbound pipeline and do not increase unread counts or send new-message notifications. Live testing showed that some returned records have Baileys `CIPHERTEXT` stubs and cannot be decrypted (`No matching sessions found` / `Bad MAC`); those placeholders are now ignored instead of being stored as empty system messages. Baileys only returns history it can access and decrypt; this request does not discover chats absent from Hala, and Cloud API has no equivalent history download here. The provider API shape was checked against the installed Baileys 6.7.24 types and implementation (`WASocket.fetchMessageHistory` takes an oldest-message timestamp in milliseconds; ON_DEMAND sync notifications are explicitly enabled).
- **Sign-in tenant selection (2026-11-09):** The web sign-in form omits the tenant slug and the API defaults to `BOOTSTRAP_TENANT_SLUG` from `.env`. The API continues accepting an optional tenant slug for multi-tenant clients; this keeps tenant selection configurable per deployment without exposing it in the standard login UI.
- **WhatsApp contact metadata (2026-11-09):** Baileys history includes contacts and emits contact upsert/update events. The worker now persists their names and phone associations within its owned tenant/account and refreshes matching conversation names. Message imports retain known names when `pushName` is absent. LID and phone JIDs resolve to an existing LID contact where possible; separate historical contacts are updated with the same metadata rather than destructively merged. WhatsApp may omit names or phone numbers, so a LID fallback remains for those contacts.
